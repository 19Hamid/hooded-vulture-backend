# Chat API reference

## Endpoint

`POST /api/chat`

Production: `https://hooded-vulture-backend.vercel.app/api/chat`

Local: `http://localhost:3001/api/chat`

Send `Content-Type: application/json`. Browser preflight uses `OPTIONS /api/chat` and receives `204` for an allowed origin.

## Request

```json
{
  "text": "Can you explain that more simply?",
  "personality": "happy",
  "sessionId": "demo-session-001",
  "history": [
    { "role": "user", "content": "Hello" },
    { "role": "assistant", "content": "Hello! Ask me about hooded vultures." }
  ]
}
```

| Field | Required | Rules |
| --- | --- | --- |
| `text` | Yes | Nonblank string, at most 2,000 characters; surrounding whitespace is trimmed |
| `personality` | No | `normal`, `happy` or `angry`; defaults to `normal` |
| `sessionId` | No | 8–128 letters, numbers, underscores or hyphens |
| `history` | No | Complete alternating user/assistant pairs; defaults to `[]` |

History allows 12 messages, 4,000 characters per message and 12,000 characters in total. Each pair starts with `user` and ends with `assistant`. System roles are rejected.

The JSON body must fit within 64 KiB. A session ID is validated but does not create a server-side conversation store.

## Success

HTTP `200`:

```json
{
  "reply": "Example assistant response.",
  "requestId": "e6fdbf75-860b-4c5f-945b-79bba1a7962c"
}
```

The reply is generated by the model. The reference also appears in `X-Request-Id`.

## Errors

```json
{
  "error": "Chat is temporarily unavailable. The service configuration needs attention.",
  "code": "PROVIDER_KEY_REJECTED",
  "requestId": "e6fdbf75-860b-4c5f-945b-79bba1a7962c"
}
```

| HTTP | Code | Meaning |
| --- | --- | --- |
| `400` | `INVALID_REQUEST` | Invalid JSON, text, personality, history or session ID |
| `403` | `ORIGIN_NOT_ALLOWED` | Origin is outside the allowlist |
| `405` | `METHOD_NOT_ALLOWED` | Method is neither POST nor OPTIONS |
| `413` | `REQUEST_TOO_LARGE` | Body exceeds the size limit |
| `415` | `UNSUPPORTED_MEDIA_TYPE` | Content type is not application/json |
| `429` | `RATE_LIMITED` | Application usage counter rejected the request |
| `429` | `PROVIDER_RATE_LIMIT` | Groq rejected the request because of a provider limit |
| `502` | `INVALID_PROVIDER_RESPONSE` | Reply is missing, blank or longer than 4,000 characters |
| `502` | `PROVIDER_UNAVAILABLE` | Connection or another unclassified provider failure |
| `503` | `SERVICE_NOT_CONFIGURED` | Backend API key is missing |
| `503` | `PROVIDER_KEY_REJECTED` | Groq rejected the key with HTTP 401 |
| `503` | `PROVIDER_ACCESS_DENIED` | Groq denied access with HTTP 403 |
| `503` | `PROVIDER_CONFIG_ERROR` | Provider returned HTTP 400, 404 or 422 |
| `503` | `RATE_LIMIT_UNAVAILABLE` | Configured Redis counters could not be checked |
| `504` | `PROVIDER_TIMEOUT` | Provider call timed out |

Rate-limit responses include `Retry-After`. Responses also set `Cache-Control: no-store` and `Vary: Origin`.

The local server can reject an oversized streamed body before the handler; that early `413` contains an error message only.

## Diagnose failures

Match the UI reference or `X-Request-Id` to the backend project's Vercel runtime log.

| Code | Check |
| --- | --- |
| `SERVICE_NOT_CONFIGURED` | Key exists in the correct backend environment; redeploy after setting it |
| `PROVIDER_KEY_REJECTED` | Replace the rejected key and redeploy |
| `PROVIDER_ACCESS_DENIED` | Groq account, project and model access |
| `PROVIDER_CONFIG_ERROR` | Model identifier and provider code in the log |
| `PROVIDER_RATE_LIMIT` | Groq quotas, spending controls and retry window |
| `PROVIDER_TIMEOUT` / `PROVIDER_UNAVAILABLE` | Retry a short request and check provider availability |
| `RATE_LIMIT_UNAVAILABLE` | Both Redis settings and Redis availability |

Logs contain the reference, configured model and safe provider status/code when available. They exclude prompts, keys and raw SDK errors.

Official references: [Groq errors](https://console.groq.com/docs/errors) and [Vercel runtime logs](https://vercel.com/docs/logs/runtime).
